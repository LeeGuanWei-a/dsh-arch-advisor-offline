# 工作流原文：文档生成与引导式设计

SKILL.md 里是摘要，这里是与 DSH 插件逐字一致的两段触发规则原文，以及六阶段设计的问题清单。拿不准流程细节时读这里。

> 本文件由 `npm run skill:refs` 从 `lib/` 数据源生成，**请勿手改**；要改内容请改数据源后重新生成。

## 1. 文档工作流（doc-workflow 原文）

> 当用户要求“生成文档 / 重新生成文档 / 重做 / 再生成 / 说明书 / 把 xx 写成文档”，且场景属于系统设计或开发文档时，按下列顺序执行（这是流程，不是建议）：【第 1 步·必做】立即调用 ask_user_question，一次问两个问题：Q1「用哪套文档体系?」选项：A 旧版 5 类（arch 架构方案 / prd 需求 / hld 概要设计 / lld 详细设计 / dbd 数据库设计）——存量项目续写、沿用老模板；B 国标版（GB/T 8567—2006 的 25 类）——新项目、对外交付、评审/投标；Q2「这批文档给谁看?」选项：内部 / 客户交付 / 投标评审。**即使本次会话之前已经生成过某套文档、也不管上一轮选了哪套，重新生成时必须重新问一次**；只有用户在**本条消息里**明确写了“旧版/国标/25 类/5 类”时才可跳过 Q1。未得到体系答案前，不得调用 arch_docs_offline 取骨架、不得落盘任何文件。【第 2 步】按选定体系调 arch_docs_offline(docType="list") 拿该体系清单与裁剪建议，让用户确认本次产出哪几份——不要默认全出（尤其是 25 类全量），也不要凭记忆自己列类型。【第 3 步】逐份 arch_docs_offline(docType=<编号或简称>, spec="legacy" 或 spec="gb") 取骨架——**spec 必填，不带 spec 会被拒绝并返回对比页**；按返回的「填写要点」填写，落盘 docs/<项目名>-<编号或简称>-<文档名>.md。【第 4 步】每份文件开头固定放「文档控制块 + 修订记录」，位置永远在正文最前面，不得改放文末；升版只在修订记录表追加一行，不生成 archive/ 副本（历史由 git 承担）。【第 5 步】严格遵守每份文档返回的「代码策略」：策略为「禁止代码」的不得出现 \`\`\` 代码块；「仅伪代码」只能写 IF/THEN 式伪代码并标注「伪代码，非交付源码」；越界代码必须改写为文字、表格或图。仅当用户要“写代码/普通回答”时不要触发此流程。

注入名：`awesome-architecture-offline:doc-workflow`，order 5100。

## 2. 设计工作流（design-workflow 原文）

> 当用户表达「想做一个 X / 帮我想个方案 / 设计一个系统 / 这个系统怎么做 / 有个想法想落地」这类"从想法起步"的架构诉求时：① 先调 arch_ask_offline(question=用户原话或提炼后的场景) 把想法映射到最相关的 教程+模板+案例，基于返回内容再展开讨论；② 需要继续推进时用 arch_design_offline 分步走（clarify→constraints→structure→decisions→roadmap→review），一次只推进一个阶段，并把已确认信息放进 context；③ 不要跳过插件、直接凭记忆一次性给整篇方案；只有工具不可用或用户明确说"不用查资料/随便聊聊"时才退回普通回答。④ 「生成文档」诉求走 doc-workflow 段，「想方案/设计方案」诉求走本段，两者不要互相顶替。

注入名：`awesome-architecture-offline:design-workflow`，order 5099。

## 3. 六阶段设计的阶段定义

### `clarify` · ① 需求澄清

**目标**：产出: 一句话系统定位 + 核心用户场景 + 范围边界(不做清单) + 触发使用的真实事件。

**要问用户的问题**：

1. 想做的这件事，谁在用、什么场景？（一句话定位）
2. 用户核心的 1-3 个动作/流程是什么？哪个是「没它产品不成立」的？
3. 第一批真实用户规模/数据量级？数据从哪来、什么形态（结构化/文档/事件）？
4. 首版明确不做什么？（登录/多语言/移动端/复杂权限先划掉）
5. 内部工具还是上线产品？时间/预算/合规（支付、隐私）约束？

**进入下一阶段的标准**：能一句话说清：是什么、给谁、做什么、首版边界。

**建议阅读**：`tutorial:02` / `tutorial:07`

### `constraints` · ② 约束与质量属性

**目标**：定 性能/可用性/一致性/成本/安全 目标与优先级，识别最强约束（通常数据一致性或外部依赖）。

**要问用户的问题**：

1. 哪些必须强一致？哪些可最终一致/异步？（支付余额 vs 点赞数）
2. 可用性要求？能接受降级吗？RTO/RPO 大概多少？
3. 量级档位: 日活/写入/数据量在 10K/1M/100M 哪档？多久到？
4. 最强外部依赖（支付/LLM/第三方 API）不可用时系统如何表现？
5. 成本敏感度：创业 MVP / 企业预算 / 极致性价比？贵组件必须省哪些？

**进入下一阶段的标准**：约束清单：强一致范围、可用性/延迟目标、量级档、最强依赖、成本画像。

**建议阅读**：`tutorial:06` / `tutorial:10` / `tutorial:11`

### `structure` · ③ 结构设计

**目标**：产出 C4 容器级草稿: 模块/存储/读写路径/边界通信，并预判瓶颈先出现在哪。

**要问用户的问题**：

1. 主干数据流：请求进→处理→落库→通知/回读 长什么样？
2. 按什么切模块：业务能力还是技术层？
3. 哪里需要队列/事件/缓存？哪里有读热点或写放大？
4. 状态放哪、谁是事实源（单一写者）？副本同步还是异步？
5. 先画「最简单能跑」的图，再标：量×10 时第一个瓶颈在哪？

**进入下一阶段的标准**：一张容器/模块图 + 主读写路径 + 最先失效点预判。

**建议阅读**：`tutorial:03` / `tutorial:04` / `tutorial:05` / `tutorial:13`

### `decisions` · ④ 关键决策与 ADR

**目标**：识别 3-5 个关键决策点，逐个写 ADR(上下文→决策→后果)，对照同类系统取舍。

**要问用户的问题**：

1. 最关键 3-5 个决策是什么？（单体还是微服务 / SQL还是文档库 / 同步还是异步 / 自研还是SaaS）
2. 每个决策的备选方案牺牲了什么？（没有免费的架构）
3. 哪个选择会锁死演进？退出方案是什么？
4. 用 arch_search_offline 找最贴近模板，精读「关键决策与权衡」。
5. 先不定具体框架名——先定这类问题的答案，再定技术。

**进入下一阶段的标准**：3-5 个 ADR（含备选与放弃项）+ 选型决策树。

**建议阅读**：`tutorial:08` / `tutorial:34`

### `roadmap` · ⑤ 演进路线

**目标**：MVP 范围、第一个升级触发信号、每个里程碑的量化指标与放弃项。

**要问用户的问题**：

1. MVP 最小闭环是哪条端到端路径？
2. 哪个量化信号（P99延迟/单表>10M/告警数）触发第一次升级？
3. 每个里程碑敢砍什么？怎么飞行中换引擎（绞杀者/灰度）？
4. 哪些升级永远不会发生？（标记「不做直到有信号」）

**进入下一阶段的标准**：MVP 路径 + 触发信号清单 + 2-3 个里程碑。

**建议阅读**：`tutorial:20` / `演进触发信号` / `tutorial:12`

### `review` · ⑥ 方案审查

**目标**：按生产级 checklist 挑毛病：失败设计/安全/一致性/可观测/权限。

**要问用户的问题**：

1. 单点故障在哪？有熔断/重试/降级/幂等吗？会级联吗？
2. 数据损坏/丢失/重复路径都补幂等与校验了吗？多租户隔离清楚吗？
3. 用户视角 SLO 定了吗？指标/日志/链路/告警怎么落地？
4. AI 组件: 输出校验/提示注入/成本失控/评测回归怎么管？
5. 给外行看 5 分钟，他能看出「哪会先崩、拿什么换什么」吗？

**进入下一阶段的标准**：一轮找茬后的修订定稿 + 遗留风险清单。

**建议阅读**：`tutorial:24` / `tutorial:12` / `tutorial:16` / `tutorial:32`

## 4. 文档控制块（每份文档开头固定使用）

```markdown
| 项 | 内容 |
| --- | --- |
| 文档标识号 | <项目编号>-<两位编号>-<简称> |
| 文档名称 | <中文名>（<简称>） |
| 版本 / 发行号 | v0.1 / R0 |
| 密级 | 内部 |
| 编制 / 审核 / 批准 | <姓名> / <姓名> / <姓名> |
| 修订记录 | v0.1 初稿（YYYY-MM-DD） |
```

修订记录表紧随其后；升版只追加一行，不建 `archive/` 副本（历史由 git 承担）。

## 5. 旧版 5 类骨架摘要

### `arch` · 架构方案（方案/ADR）

用途：系统从想法到方案的第一份文档；回答“为什么这么做”。前置用 arch_ask_offline/arch_design_offline 引导讨论。

章节：

- **1. 系统定位** — 一句话定位 + 表格：使用方/触发方式/数据形态/范围边界/不做清单（核心用户动作必做项）
- **2. 约束与质量属性** — 一致性/可靠性/校验模式/审计/性能/成本 的目标表；标注“最强约束”
- **3. 总体架构** — ASCII 容器图 + 模块清单表（模块/职责/要点）+ 数据模型核心表 + 批次/流程状态机
- **4. 关键决策 ADR** — 编号表：决策点/采纳方案/放弃的备选与代价；标注“演进锁死点”
- **5. 里程碑** — M1..Mn 阶段表（内容/验收）+ “本次不做，直到有信号”清单
- **6. 审查与遗留风险** — 已覆盖项（失败设计/幂等/权限/一致性/可观测）+ 编号风险清单 R1..Rn
- **7. 参考来源** — 引用的 arch_read_offline 条目/模板/案例，供追溯

完成标准：

1. 给外行看 5 分钟能看出：哪会先崩、拿什么换什么
2. 每个 ADR 都写了放弃的备选
3. 里程碑含触发升级的量化信号

样例：参考 金融数据加工系统 实战样例（架构方案.md）

### `prd` · 需求文档（PRD）

用途：回答“做什么”；从 arch_design_offline clarify/constraints 阶段的结论落笔。业务规则必须精确到可开发。

章节：

- **1. 文档信息与版本** — 版本号 + 变更历史（每版写清相对上版改了什么）
- **2. 背景与目标** — 为什么做 / 目标清单 / 成功标准 / 非目标（不做清单）
- **3. 术语表** — 统一业务/技术术语，避免歧义
- **4. 用户角色与使用场景** — 角色表（动作/频率）+ 关键场景 S1/S2/S3 走查
- **5. 总体需求** — 范围图 + 核心规则总表（各业务模块 字段/L1校验/L2比对）
- **6. 功能需求** — 文件导入与批次/自动校验(L1)/错误明细与重跑/业务模块需求(按模块细化到字段表)/跨业务比对(L2)/审批复核/统计报表/审计
- **7. 非功能需求** — 一致性/可靠性/性能/审计合规/安全/可用性 目标表
- **8. 权限与角色** — RBAC 权限点矩阵
- **9. 边界与不做清单** — 首版明确不做
- **10. 验收标准** — 可测试条目清单
- **附录A 待确认问题清单** — A-1..An：未定事项显式列出（建议带默认值），避免开发带问号开工
- **附录B 业务回填模板** — 其余业务按统一模板补充

完成标准：

1. 每个业务字段表含：类型/必填/校验规则
2. L1(字段级)与L2(跨模块)两层校验分开写清失败处理（是否入库！）
3. 未定项都在附录A且给了建议默认
4. 版本历史记载每版变更

样例：参考 金融数据加工系统 实战样例（需求文档 v0.1→v0.3 演进）

### `hld` · 概要设计（HLD）

用途：回答“怎么做的大结构”：模块划分、核心流程与状态机、接口清单、数据概要。与 prd/arch 一一对应。

章节：

- **1. 设计目标与约束回顾** — 从 prd/arch 摘录关键约束（勿重复大段正文）
- **2. 逻辑架构与模块划分** — 工程结构树 + 组件职责表 + 扩展 SPI 说明
- **3. 核心流程设计** — 状态机图 + 主链路时序(ASCII) + 关键机制（幂等/断点续跑/重跑/归档）
- **4. 数据设计（概要）** — schema 布局 + 核心表 + 关键索引/查询说明
- **5. 接口清单** — 对外 REST 表(方法/路径/说明/权限) + 内部 SPI
- **6. 关键技术决策** — HD-1..n 表（决策/理由/影响）
- **7. 部署视图** — 概念部署图 + 并发/恢复策略
- **8. 风险与待定项** — P1..Pn（项/影响/归属文档）

完成标准：

1. 状态机覆盖异常分支与重跑语义
2. 每个 prd 业务需求都能找到对应模块/流程
3. 跨模块交互（比对/审批）有时序

样例：参考 金融数据加工系统 实战样例（概要设计.md）

### `lld` · 详细设计（LLD）

用途：回答“具体怎么实现”，细到类/接口/方法签名/关键逻辑，开发可直接编码；测试据此写用例。

章节：

- **1. 总体包结构** — 细化到包/目录
- **2. 领域模型与枚举** — 核心实体字段 + 状态枚举与合法流转
- **3. 框架机制** — 动态schema路由/事务边界/审计切面 等实现方案
- **4. 核心引擎详细设计** — 批处理编排/幂等守卫/分批提交与断点续跑 等：伪代码+关键方法
- **5. 校验引擎** — L1 规则链接口 + 内置规则 + L2 比对执行（含“失败仍入库”的落点）
- **6. 业务模块实现** — SPI 契约 + 各业务具体类定义
- **7. 审批旁路** — Flowable 触发/回调/事务边界
- **8. 审计/报表/Web/安全** — 按模块细化
- **9. 错误码** — code/含义 表
- **10. 并发与线程模型** — 锁/线程池/限流
- **11. 测试关注点** — 给测试的重点场景编号列表
- **12. 需求变更记录** — 确认项→回填位置 表

完成标准：

1. 每条特殊业务规则都能在代码位置找到实现锚点
2. 测试关注点覆盖需求里所有“差异点/边界”
3. 错误码覆盖主要失败路径

样例：参考 金融数据加工系统 实战样例（详细设计.md）

### `dbd` · 数据库设计

用途：数据落点：schema/表/索引/DDL 草案/约定。字段以需求文档为准，禁止自行发明。

章节：

- **1. 总览** — schema 布局表 + 命名约定（表统一名便于路由/跨库查询）
- **2. common 表** — 批次/错误明细/审计/文件副本/锁 等，含索引与幂等查询注释
- **3-5. 各业务 schema** — 每模块主表(有效行) + 归档表(history) 的结构与索引、业务字段注释
- **6. 索引与查询说明** — 每个关键查询 → 命中索引 对照表
- **7. DDL 约定** — 金额decimal/时间精度/字符集/归档重跑/迁移工具
- **8. 外部引擎表** — Flowable 等自带表放独立 schema
- **9. 需求变更记录** — 确认项→DDL 落点

完成标准：

1. 字段与需求文档逐项一致（含“仅必填不验格式”等特殊规则）
2. 唯一索引语义与“主表只留有效行/归档”一致
3. 金额字段类型/精度标注清晰

样例：参考 金融数据加工系统 实战样例（数据库设计.md）
